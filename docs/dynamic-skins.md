# Skins that follow the system palette

AndAmp Dark and AndAmp Light are generated by the Python build in `skin/`. The build also
writes each skin as a template: the same pixels with the colors replaced by named roles. On
Android 12 and later the player rebuilds the two skins from the phone's dynamic
`ColorScheme` through that template. No drawing code is duplicated in Kotlin.

The result is a classic Winamp skin: the same twenty sheets, the same `PLEDIT.TXT`,
`VISCOLOR.TXT` and `REGION.TXT`, and the same sprite coordinates. The windows, the widget,
the skin browser and the preview receive an ordinary `Skin`.

## The template

[`skin/docs/runtime-theming.md`](../skin/docs/runtime-theming.md) describes the template
format and the measurements behind it. Two properties matter here:

- The role image is the same for dark and light: 419,442 pixels, each holding a role index.
  The two themes differ only in which color four role aliases bind to (`win_hover_fill`,
  `win_hover_ink`, `vis_floor` and `current_track` in `skin/andamp/palette.py`).
- Binding the role image to the shipped palette reproduces the shipped `.wsz` byte for byte,
  for every theme and every sheet.

At run time the player resolves 110 roles against a `ColorScheme` and writes one `IntArray`
per sheet through that table. `skin/dist/andamp-<theme>-template.zip` is about 14.7 KB.

## Data flow

```
skin/ (Python)                     :app
──────────────                     ─────
build.py all                       assets/skins/  (copied by :app:bundledSkins)
  ├─ AndAmp Dark.wsz      ────────▶   AndAmp Dark.wsz          static, the fallback
  ├─ AndAmp Light.wsz     ────────▶   AndAmp Light.wsz         static
  ├─ AndAmp Spot.wsz      ────────▶   AndAmp Spot.wsz          static
  ├─ andamp-dark-template.zip  ───▶   andamp-dark-template.zip
  └─ andamp-light-template.zip ───▶   andamp-light-template.zip
                                        │
                     SystemPalette ─────┤   dynamicDark/LightColorScheme, API 31+
                                        ▼
                                   SkinTemplate.colors()     110 colors
                                        ▼
                                   SkinTemplate.bitmaps()    20 sheets
                                        ▼
                                   SkinAssembly.assemble()   shared with SkinLoader
                                        ▼
                                        Skin
```

Spot's template, the role tables and the previews in `skin/dist` are not bundled.

## Which skins are live

AndAmp Dark and AndAmp Light are one entry each in the Skins menu, with the same id and
name on every phone. On Android 12 and later, with the setting on, the entry is built from
the phone's palette. Below API 31, or with the setting off, the entry is the shipped `.wsz`.

The setting is Preferences > Player > Colors > Match wallpaper colors. It is on by default,
and the row is shown only on Android 12 and later. `PaletteStore` holds it in its own
preferences file, which the app and the widget both read. `CurrentSkin.live` applies it,
because the skin package does not depend on the state package.

AndAmp Spot is always static. Its colors are fixed seeds (an LCD green and an amber for the
analyzer).

Each live entry asks for its own scheme (`LiveTemplate.dark` in `BundledSkins`): Dark
resolves the dynamic dark scheme and Light the dynamic light scheme, whatever the phone's
night mode is.

## The classes

All are in `nl.mattix.andamp.skin` unless another package is named.

- **`SkinTemplate` and `Tonal`.** The run-time half of the template. They contain no
  geometry. `Tonal` is a port of `skin/andamp/tonal.py`, so that both implementations
  produce the same numbers.
- **Contrast pairs.** The template's manifest lists the 34 declared contrast pairs by role
  name, and loading refuses a pair that names a role the table does not have. Pairs are
  kept by name because several roles share one color under the baseline palette and
  differ under a live scheme.
- **`SystemPalette`.** The only place that reads dynamic color. It is not a Composable,
  because the widget has no composition. It returns `dynamicDarkColorScheme` or
  `dynamicLightColorScheme` on API 31 and later, and null below, and null makes an entry
  fall back to its file. It reads through the package's current resources, because a newly
  installed package receives its color overlays shortly after its process may have
  started.
- **`SkinAssembly`.** Everything that happens after a skin's parts are decoded: per-sheet
  fallback, balance borrowing volume's art, the `GEN.BMP` font scan, `PLEDIT` and
  `VISCOLOR` parsing, and regions. `SkinLoader` reads a zip and calls it; the live path
  writes bitmaps and calls it.
- **`LiveSkins`.** Turns a bundled entry and a palette into a `Skin`. `stamp` resolves the
  palette through the template. `build` writes bitmaps only when the stamp has changed and
  returns the same instance for the same palette. A build writes 419,442 pixels, about
  1.7 MB of bitmaps, and `SkinOps` runs it off the main thread.
- **`CurrentSkin`** (`nl.mattix.andamp.state`). The fallback order that the app and the
  widget share: a live skin from the palette, then the stored skin, then the bundled one.
  Its `cacheKey` includes the palette's stamp, so a changed wallpaper gives a changed key.

### Colors of the Material screens

`rememberSkinColorScheme(skin)` normally derives a Material scheme from the skin's art. A
live skin carries the scheme it was built from (`Skin.liveScheme`), and that scheme is used
directly. Static skins have no scheme, so theirs is derived from the art.

## When the palette changes

| What changed | App | Widget |
|---|---|---|
| The wallpaper, or dynamic color on or off | `SkinOps.paletteChanged`, from a configuration change | redrawn by the app; its cache key includes the palette |
| The Match wallpaper colors switch | `SkinOps.paletteChanged` | redrawn by the app |
| The listener picks another skin | `SkinOps.applyAt` | redrawn by the app |

`SkinOps` registers `ComponentCallbacks` on the application, so a configuration change
reaches it whichever activity is showing. `paletteChanged` compares the base skin's stamp
with the previous one and does nothing when it is unchanged, as after a rotation.
Otherwise it rebuilds the base skin, reloads the worn skin and calls
`MainWindowWidget.refresh`.

## Contrast

`SkinTemplate.colors(scheme, repair = true)` checks every declared pair. When a pair comes
out under its required ratio, it moves the foreground along its tone axis until the pair
passes. `repair` is on by default. `skin/verify/sweep.py` runs the pairs against synthetic
schemes; run it after a palette change.

## Tests

1. `SkinTemplateRolesTest` resolves the roles against Material 3's baseline scheme and
   compares them with `skin/dist/andamp-<theme>-roles.json`, the same table resolved by
   Python.
2. `SkinTemplateBitmapsTest` binds the template to the shipped palette and compares every
   sheet with the BMP inside the shipped `.wsz`. A failure means the two implementations
   differ, or `skin/` changed without `python3 skin/build.py all`.
3. `SkinTemplateContrastTest` asserts that the manifest names both roles of every pair,
   that the shipped palettes pass every pair without repair, and that every pair holds
   under synthetic schemes with repair on.
4. `SkinAssemblyParityTest` asserts that a skin rebuilt from its template equals the one
   loaded from its file.
5. `WindowGoldenTest` loads the shipped `.wsz`, so the goldens do not depend on a
   wallpaper. One golden, `main window live baseline`, renders the live base skin bound to
   the baseline scheme.

## What stays in Python

Everything that decides how the skin looks: the sheets, the shape scale, the icon masks,
`verify` and `audit`. The template is an output of that build. Run
`python3 skin/build.py all` after a change in `skin/`; otherwise the template describes the
previous skin and `SkinTemplateBitmapsTest` fails.
